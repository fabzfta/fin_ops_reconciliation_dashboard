# FinOps Reconciliation Platform
### Financial Data Integration & Reconciliation Platform

FinOps AI is an end-to-end data engineering project that simulates the financial data lifecycle of a B2B SaaS company across CRM, billing, payment processing, and accounting systems.

The platform integrates data from **HubSpot, Stripe, and QuickBooks Online**, preserves immutable raw API responses, transforms the data through a layered **dbt** architecture, resolves customer identities across systems, and performs deterministic financial reconciliation.

A **Streamlit dashboard** provides visibility into the financial close process, including invoice reconciliation, payment reconciliation, settlement validation, processing fees, foreign exchange conversion, transaction lineage, and reconciliation exceptions.

The project was designed to demonstrate how a modern data platform can support finance teams by turning fragmented operational data into an auditable and traceable financial control system.

---

## Business Problem

A SaaS company's financial lifecycle is usually distributed across multiple systems.

A typical customer may originate in a CRM such as HubSpot, be billed through Stripe, and ultimately be recorded in an accounting platform such as QuickBooks.

This creates several reconciliation challenges:

- Does the invoice generated by the billing platform match the accounting system?
- Was the customer payment correctly recorded?
- Can a payment be traced back to the original CRM deal?
- Do processor settlement amounts reconcile after fees?
- How are currency conversions represented?
- Can discrepancies be detected automatically?
- Can finance teams trace every financial event back to its source?

FinOps AI creates a unified data model to answer these questions.

# API Integrations

## HubSpot

HubSpot represents the CRM layer.

The ingestion pipeline retrieves:

- Companies
- Contacts
- Deals

The project creates explicit relationships between the customer and the commercial opportunity.

Example lineage:

```text
HubSpot Company
      │
      ├── Contact
      │
      └── Deal
```

The deal represents the commercial origin of the financial lifecycle.

---

## Stripe

Stripe represents subscription billing and payment processing.

The platform retrieves:

- Customers
- Invoices
- Payment Intents
- Charges
- Balance Transactions

Stripe provides an important financial lineage:

```text
Invoice
   │
   ▼
Payment Intent
   │
   ▼
Charge
   │
   ▼
Balance Transaction
```

This allows the platform to distinguish between three concepts that should not be modeled as the same event:

```text
Invoice ≠ Payment ≠ Settlement
```

An invoice represents the amount billed.

A payment represents money collected from the customer.

A settlement represents the processor's financial movement after fees and, potentially, currency conversion.

---

## QuickBooks Online

QuickBooks represents the accounting system.

The platform integrates:

- Customers
- Items
- Invoices
- Payments
- Chart of Accounts setup

OAuth 2.0 is used for authorization.

Stripe identifiers are preserved when accounting records are created, allowing deterministic reconciliation between the billing and accounting systems.

# Raw Data Architecture

All API responses are preserved before transformation.

Raw files follow a partitioned structure:

```text
data/raw/
├── hubspot/
│   ├── companies/
│   ├── contacts/
│   └── deals/
│
├── stripe/
│   ├── customers/
│   ├── invoices/
│   ├── payment_intents/
│   ├── charges/
│   └── balance_transactions/
│
└── quickbooks/
    ├── customers/
    ├── invoices/
    └── payments/
```

Each ingestion run receives a unique `run_id`.

Example:

```text
data/raw/stripe/invoices/
    ingestion_date=YYYY-MM-DD/
        run_id=<RUN_ID>/
            <SOURCE_RECORD_ID>.json
```

This provides:

- reproducibility;
- auditability;
- source-level lineage;
- ingestion history;
- debugging capability.

Raw API payloads are not modified by downstream transformations.

---

# PostgreSQL RAW Layer

Raw objects are loaded into:

```sql
raw.api_records
```

The table stores ingestion metadata alongside the original JSON payload.

Conceptually:

```text
source_system
entity_type
source_record_id
ingestion_date
run_id
raw_object_path
payload JSONB
loaded_at
```

The combination of:

```text
source_system
entity_type
source_record_id
run_id
```

provides ingestion-level idempotency.

This prevents the same source object from being inserted twice during the same ingestion run.

- source identifier preservation.

Stripe monetary values are converted from minor currency units into standard decimal amounts during staging.

Cross-system business logic is intentionally excluded from this layer.

# Entity Resolution

One of the central challenges is identifying the same customer across independent systems.

For example:

```text
HubSpot
Company ID
      │
      ▼
Stripe
Customer ID
      │
      ▼
QuickBooks
Customer ID
```

The project avoids fuzzy matching based on company names or email addresses.

Instead, explicit source metadata and financial lineage are used to build a deterministic identity map.

Conceptually:

```text
internal_client_id
        │
        ├── HubSpot Company ID
        ├── Stripe Customer ID
        └── QuickBooks Customer ID
```

The internal identifier is deterministic and generated from the source identity.

This mapping is represented by the `identity_map` model.

# Multi-Currency Processing

The project deliberately preserves transaction and settlement currencies separately.

For the example transaction:

```text
Customer Charge
$5,000 USD

        │
        │ FX
        ▼

Processor Gross
R$ 25,838.30

        │
        ├── Processing Fees
        │   R$ 1,548.11
        │
        ▼

Processor Net
R$ 24,290.19
```

The platform does not treat these values as interchangeable.

The model stores:

```text
charge_amount
charge_currency

settlement_gross
settlement_fee
settlement_net
settlement_currency

exchange_rate
```

This is important for accounting accuracy and financial reconciliation.

# Reconciliation Engine

The analytics layer combines the financial facts into a deterministic reconciliation model.

The main model is:

```text
reconciliation_summary
```

It evaluates three independent controls.

### Invoice Control

```text
Stripe Invoice
vs.
QuickBooks Invoice
```

### Payment Control

```text
Stripe Payment
vs.
QuickBooks Payment
```

### Settlement Control

```text
Gross
-
Processing Fees
=
Net Settlement
```

If every control passes:

```text
RECONCILED
```

If one or more controls fail:

```text
EXCEPTION
```

with a corresponding reason such as:

```text
INVOICE_MISMATCH
PAYMENT_MISMATCH
SETTLEMENT_MISMATCH
```

Financial calculations remain deterministic SQL logic rather than application or AI-generated decisions.

# Controlled Exception Simulation

A financial control system should demonstrate more than a successful happy path.

The project therefore contains controlled test scenarios.

For example:

```text
Stripe Invoice       $5,000
QuickBooks Invoice   $4,900
                     -------
Difference             $100
```

The reconciliation engine identifies:

```text
Status:
EXCEPTION

Reason:
INVOICE_MISMATCH
```

Test scenarios are isolated from the real source data.

They do not modify:

- raw API responses;
- core financial facts;
- original QuickBooks records;
- Stripe transactions.

This allows exception handling to be demonstrated without corrupting the underlying financial dataset.

# Running Locally

## 1. Clone the repository

```bash
git clone <repository-url>
cd <repository>
```

## 2. Create a virtual environment

```bash
python -m venv venv
```

Activate it.

Windows:

```powershell
.\venv\Scripts\Activate.ps1
```

## 3. Install dependencies

Install the Python dependencies required by the project.

```bash
pip install -r requirements.txt
```

## 4. Configure environment variables

Create:

```text
.env
```

based on:

```text
.env.example
```

API credentials and OAuth tokens must never be committed to source control.

## 5. Start PostgreSQL

```bash
docker compose up -d
```

## 6. Run ingestion workflows

The ingestion workflows are available under:

```text
src/workflow/
```

They retrieve operational data and persist immutable API responses into the RAW layer.

## 7. Load RAW data into PostgreSQL

```powershell
$env:PYTHONPATH="src"
python src/workflow/load_raw_to_postgres.py
```

## 8. Run dbt

From the `dbt` directory:

```bash
dbt run --profiles-dir .
dbt test --profiles-dir .
```

To load controlled demo scenarios:

```bash
dbt seed --profiles-dir .
dbt run --profiles-dir .
```

## 9. Start the dashboard

From the project root:

```bash
streamlit run dashboard/app.py
```

The dashboard will be available locally through Streamlit's development server.

# Design Principles

The project follows several principles.

### Preserve source data

RAW data should remain immutable and reproducible.

### Separate ingestion from transformation

API clients should not contain warehouse business logic.

### Preserve financial grain

Invoices, payments, charges, and settlements represent different financial events.

### Prefer deterministic identity resolution

Explicit identifiers and metadata are preferred over fuzzy matching.

### Keep financial controls deterministic

Reconciliation logic belongs in SQL/dbt rather than dashboards or generative AI.

### Make exceptions visible

A financial data platform should highlight what failed, not only what succeeded.

### Maintain lineage

Every important financial value should be traceable back to its operational source.

# Why This Project Matters

Financial data engineering is not only about moving data between systems.

A reliable financial platform must answer:

```text
Where did this number come from?

Does it match the source system?

Does accounting agree with billing?

Was the customer payment recorded?

What did the payment processor actually settle?

What fees were charged?

Was currency conversion involved?

If something does not reconcile, where did it break?
```

FinOps AI was built around those questions.

The result is a small but complete example of how data engineering can connect operational systems, accounting data, and financial controls into a traceable reconciliation platform.
